# TASK-0209: Generate or maintain the API OpenAPI document, executable HTTP examples, and portal-consumable typed or Zod validators for the accepted v1 surface

## Objective

Generate or maintain the API OpenAPI document, executable HTTP examples, and portal-consumable typed or Zod validators for the accepted v1 surface.

This task contributes to [EPIC-02: Versioned Contracts](../epics/EPIC-02.md)
and must preserve the epic outcome: Freeze interoperable request, response, error, authentication, idempotency, and pagination contracts before API and agent implementations diverge.

## Dependency Context

### Prerequisites

- [TASK-0202](./TASK-0202.md): Define machine registration request/response DTOs, durable `AgentId`, registration status, assigned `MachineId`, and conflict behavior
- [TASK-0203](./TASK-0203.md): Define heartbeat DTOs for machine metadata, sequence number, sent time, agent start, boot time, CPU, memory, and storage
- [TASK-0204](./TASK-0204.md): Define owner login, device login, refresh, revoke, and API-key issue/rotate responses without exposing stored secrets
- [TASK-0205](./TASK-0205.md): Define owner read and administration contracts for device accounts, machines, sessions, and telemetry with bounded pagination and filtering
- [TASK-0206](./TASK-0206.md): Define power-meter registration, power reading, location, monitored-device, and effective-dated association contracts
- [TASK-0207](./TASK-0207.md): Define idempotency keys: `AgentId + SequenceNumber` for heartbeats and meter identity plus `MessageId` for readings
- [TASK-0208](./TASK-0208.md): Standardize validation errors on Problem Details, correlation headers, UTC timestamp format, numeric units, and unsupported payload-version responses

### Tasks Unblocked

- [TASK-1101](./TASK-1101.md): Adapt existing Next.js authentication to the owner API flow and establish typed service modules with runtime validation from the accepted OpenAPI contract

## Status (In Progress)

- **2026-08-31 — delivered so far:**
  - **OpenAPI approach:** the repository already generates its OpenAPI
    document from code at `/openapi/v1.json`
    (`OpenApiDocumentGenerator` + Scalar behind the `OpenApiEnabled` feature
    flag). That generator is the maintained document; it will describe each
    v1 route as its owning epic implements it, keeping one source of truth
    rather than a hand-authored parallel spec.
  - **Executable HTTP examples:**
    `src/SystemUptimeTracker/SystemUptimeTracker.Api/SystemUptimeTracker.Api.v1.http`
    covers login, refresh, revoke, device-account creation, registration,
    heartbeat, machine reads, meter registration, Basic Auth power reading,
    and association creation using the pinned golden payloads.
  - **Portal validators:** `SystemUptimeTracker.Web/src/utils/api-contracts/v1.ts`
    (Zod schemas for the v1 surface, pagination bounds, error contract
    constants) with `v1.test.ts` validating the same golden fixtures as the
    .NET golden tests — so a contract change fails CI on both stacks.
  - **CI:** the `contracts` job runs the golden JSON suite (66 tests) and the
    `web` job runs the Zod validator tests. Verified on GitHub Actions run
    33418707520 (2026-08-31): both jobs green, and dispatch run 33442875156
    proved a contract-test failure blocks the contracts job.
- **Remaining to complete this task:**
  - Add the CI check that fetches the generated `/openapi/v1.json` (Aspire or
    TestHost-hosted) and verifies route inventory, schemas, required fields,
    and response codes against the accepted catalog — actionable once the
    first v1 endpoints exist (EPIC-04/EPIC-05).
  - Verify the `.http` examples execute against the running API at that
    point, and capture the CI run as acceptance evidence.
