## Completion Evidence

- **Completed:** 2026-08-31.
- **Decision (aligned to the existing, test-covered implementation):** every
  non-2xx response is RFC 9457 Problem Details (`application/problem+json`)
  enriched with `traceId` and `requestId` extensions; correlation uses
  inbound W3C `traceparent` plus the `X-Trace-Id` response header stamped on
  **every** response by `RequestTraceEnrichmentMiddleware`; validation errors
  use the ASP.NET Core `ValidationProblemDetails` shape; timestamps are UTC
  ISO 8601 (server emits `+00:00`); one unit convention (bytes, percent
  0–100, watts, volt-amps, volts, amps, hertz, watt-hours, Celsius, seconds)
  with unit names embedded in field names; unsupported `payloadVersion` is
  `422` with type `urn:systemuptimetracker:error:unsupported-payload-version`.
- **Deliverables:** `SystemUptimeTracker.Contracts` `V1/ErrorContract.cs`
  (wire constants shared by agents/portal tooling), updated conventions in
  [docs/api-contracts.md](../../api-contracts.md) (errors, correlation,
  timestamps, units).
- **Tests:** `ErrorContractTests` pins the constants (contract suite 66/66
  passing); the API-side behavior is already covered by
  `RequestTraceEnrichmentMiddlewareTests`, `ProblemExceptionHandlerTests`,
  and `CustomExceptionHandlerMiddlewareTests` (green in the recorded 158/158
  run). Endpoint-level assertions for each new v1 route land with the owning
  endpoint tasks.
- **Security review:** Problem Details carry correlation identifiers only;
  `BuildUserMessage` produces generic messages, and no secrets or internal
  exception detail reach callers.
