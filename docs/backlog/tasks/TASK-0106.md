## Acceptance Criteria

- A failing test or build blocks its owning job; job output identifies the failed slice.
- All prerequisite behavior remains passing after this change.
- No credentials, API keys, refresh tokens, or sensitive configuration values
  are committed, persisted in plaintext, or emitted to logs.
- Failures are explicit and actionable; the implementation does not silently
  discard telemetry, authorization failures, migration errors, or installer
  errors.

## Validation

1. Run focused tests that directly falsify the objective if it is incomplete.
2. Run integration tests for every changed database, HTTP, authentication,
   queue, or process boundary.
3. Run platform packaging tests when Windows Service or systemd behavior is
   affected; a successful compile alone is insufficient.
4. Run portal lint, unit, browser, and automated accessibility checks when UI
   behavior is affected, followed by a manual keyboard review.
5. Run the repository-level build and the checks required by Gate 0.

## Status (In Progress)

- **2026-08-30:** `.github/workflows/ci.yml` was authored with two
  independent, cached validation slices:
  - **`.NET build and tests`** — Ubuntu runner, .NET 10 SDK, NuGet package
    caching, an ephemeral SQL Server 2022 container with a per-run generated,
    masked sa password (never committed or persisted), bounded readiness
    polling, then `dotnet build` and `dotnet test` of
    `SystemUptimeTracker.Tests` using the
    `SystemUptimeTracker__Tests__SqlServer__ConnectionString` override.
  - **`Web lint, tests, and build`** — Node 24 with npm caching, `npm ci`,
    `npm run lint`, `npm run test`, `npm run build`.
  - Future slices are reserved for their owning tasks and documented in the
    workflow header: contracts (TASK-0209), migrations (TASK-0307), QA
    journeys (TASK-1108), packaging (TASK-0909/TASK-1007).
- **Remaining to complete this task:** push the workflow and capture the
  acceptance evidence from GitHub Actions — a green run for both jobs and a
  demonstration that a failing test or build blocks its owning job with the
  failed slice identified in the job name/output. Pushing requires
  maintainer approval per repository policy, so this task stays `in-progress`
  until that run is observed.
