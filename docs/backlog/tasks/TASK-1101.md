# TASK-1101: Adapt existing Next.js authentication to the owner API flow

## Objective

Adapt existing Next.js authentication to the owner API flow; keep refresh credentials server-side or in secure `HttpOnly`, `Secure`, and appropriate `SameSite` cookies.

This task contributes to [EPIC-11: Owner Portal MVP](../epics/EPIC-11.md)
and must preserve the epic outcome: Deliver an accessible owner workflow for authentication, device accounts, machine inventory, heartbeat history, and runtime sessions through the shared API only.

## Dependency Context

### Prerequisites

- [TASK-0401](./TASK-0401.md): Map existing `Admin`, `Manager`, `Contributor`, and `Read` roles to the decided `Owner` and telemetry-only device policies
- [TASK-0404](./TASK-0404.md): Implement device credential exchange and refresh-token rotation with configured access/refresh lifetimes and revocation

### Tasks Unblocked

- [TASK-1102](./TASK-1102.md): Implement CSRF protection for cookie-authenticated state changes and tightly scoped CORS when portal and API origins differ
- [TASK-1103](./TASK-1103.md): Build device-account list/create/edit/disable/delete/reassign and API-key rotate/revoke flows, with one-time key presentation
- [TASK-1104](./TASK-1104.md): Build paginated machine inventory and detail views showing registration, last seen, OS, version, and assigned account
- [TASK-1106](./TASK-1106.md): Normalize API Problem Details into actionable field and page errors

## Acceptance Criteria

- Browser tests prove login, logout, expiry, refresh, and anonymous redirect without local-storage tokens.
- All prerequisite behavior remains passing after this change.
- No credentials, API keys, refresh tokens, or sensitive configuration values
  are committed, persisted in plaintext, or emitted to logs.
- Failures are explicit and actionable; the implementation does not silently
  discard telemetry, authorization failures, migration errors, or installer
  errors.

## Validation

2. Run integration tests for every changed database, HTTP, authentication,

3. Run platform packaging tests when Windows Service or systemd behavior is
   affected; a successful compile alone is insufficient.
4. Run portal lint, unit, browser, and automated accessibility checks when UI
   behavior is affected, followed by a manual keyboard review.
5. Run the repository-level build and the checks required by Gate 1.
